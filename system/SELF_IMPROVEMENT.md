> 系统的每一次使用，都是一次改进它的机会。
> 用了不顺手却不修，是最大的浪费。

---

## 1. 改进循环

```text
使用中发现摩擦 → 随手记录 → 每周复盘归类 → 修改模块 → CHANGELOG 记账 → 下周验证
```

**摩擦**指任何这些时刻：

- 同一段背景第二次向 AI 解释（→ 该进 IDENTITY 或 knowledge）
- 同一类任务第二次从头写指令（→ 该进 prompts/ 或 templates/）
- 成品返工超过一轮（→ 对应模板/规则不够好）
- AI 的输出违背了预期却没有规则约束它（→ RULES 或引擎缺条款）
- 找一个文件超过 1 分钟（→ 目录或命名有问题）

## 2. AI 的职责（每次会话都生效）

1. **发现即提议**：会话中察觉上述摩擦，任务完成后用一句话提议改进：「建议：把 X 沉淀为 prompts/teaching/P-T-xxx」。每次会话最多提 2 条，不刷存在感。
2. **执行有痕**：被批准的修改，动完文件必须在 `CHANGELOG.md` 的 `[Unreleased]` 记一行。
3. **不擅改内核**：`system/` 六件套的修改必须经 Anthony 明确批准；其他目录的小幅增补可以在会话内直接做（仍要记账）。
4. **提议要具体**：说清改哪个文件、加什么内容、解决什么摩擦；「建议优化 prompt 库」这类空话禁止。

## 3. 沉淀协议（什么东西写回哪里）

| 会话产出 | 写回位置 | 判断标准 |
|---|---|---|
| 好用的指令 | `prompts/<领域>/` | 未来还会用第二次 |
| 成品的骨架 | `templates/` | 同类成品会反复做 |
| 多步骤的做法 | `workflows/` | 步骤 ≥3 且顺序重要 |
| 逐项核对点 | `checklists/` | 漏一项会出事 |
| 新的稳定事实 | `knowledge/` 或 `IDENTITY` | 见 MEMORY.md 分层口诀 |
| 一次性内容 | 不沉淀 | 宁缺毋滥，库里全是精品 |

## 4. 复盘节奏

- **每周**（约 20 分钟）：跑 `checklists/weekly_review.md` —— 处理本周摩擦记录、刷新 L3 记忆、归档 CHANGELOG。
- **每月**：检查各模块「最后核对」日期；淘汰一个月未用的草稿内容；给 ROADMAP 打进度。
- **每季**：审视目录结构本身 —— 分类还合理吗？哪个领域该独立成新引擎？哪个引擎名存实亡该合并？

## 5. 版本纪律

- 语义化版本，全系统一个号（规则见 CHANGELOG.md 头部）。
- 发布节奏：每完成 ROADMAP 一周的目标 → 次版本 +1；日常修补攒着，随下次发布一起归档。
- 大改（目录重组、协议变更）前先在 ROADMAP 的 Backlog 立项，想清楚再动手 —— **演进，不推倒重来**。
